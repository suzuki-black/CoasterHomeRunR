# SDCC と R800 でできることの調査(2026-10-03)

このプロジェクトは最初から Z80 向け(`-mz80`)でコンパイルしていて、SDCC の R800 向けのポート(`-mr800`、4.4.0 で追加)を
確かめないまま進めていた。入っている SDCC 4.6.0 で、R800 向けのポートと、速さに関わるオプション・関数の属性を調べた。

## 1. 調べ方

- SDCC のマニュアル(sdccman、4.3 節「Z80 ... R800 ports」、3.3.9〜3.3.10 節、3.5.12 節)と、R800 向けのライブラリのソースを読んだ。
- プロジェクトのファイルは変えず、オプションだけを変えた ROM をスクラッチに作って比べた。
- 速さ: make pcprof を PROF_FRAMES で、実機のファームウェアの機種(My_FS-A1ST_512K)の同じフレームの範囲
  (ステージ 1: 600〜1200、ステージ 3: 300〜800)。**無敵(NO DAMAGE)にしてライフが減らない条件**で測った(下の 5 を参照)。
- 絵: tools/frame_dump.tcl で、今の版と VRAM の中身が全フレーム一致するか(ステージ 1・3、80 枚ずつ)。

## 2. R800 向けのポート(-mr800)が変えること

| 項目 | 内容 |
|---|---|
| 掛け算 | `int` どうしの掛け算を R800 の `multuw` / `multu` で出す。16×16→32 ビットのライブラリ(`__muluint2ulong` など)も `multuw` になる(Z80 版は 1 ビットずつのループ) |
| レジスタ | IXH・IXL・IYH・IYL を使う(このプロジェクトの C で 48 か所。Z80 向けでは 0) |
| 割り算 | ライブラリは Z80 版と同じ(R800 には割り算の命令がない) |
| オプション | Z80 向けと同じ並び。R800 だけのオプションはない |
| 呼び出しの約束 | Z80 向けと同じ sdcccall(1)。アセンブラで書いた関数はそのまま使える |

このプロジェクトでは、重い掛け算はもともとアセンブラ(`fmul`・`qmul`・`project2` など)で R800 の掛け算命令を使っているので、
`-mr800` が変えるのは C の中の一部と、32 ビットの積のライブラリだけだった。

## 3. 結果(1 フレームあたり)

| 版 | オプション | ステージ 1 | ステージ 3 | 絵 | 常駐部 / 地形モジュール | コンパイル |
|---|---|---|---|---|---|---|
| A | 今のまま(`-mz80 --max-allocs-per-node 5000`) | 58.06ms | 85.35ms | — | 14,753 / 10,348B | 約 1 分 |
| B | `-mr800` | 57.18ms(−0.9) | 84.41ms(−0.9) | 一致 | 14,872 / 10,348B | 約 1 分 |
| D | `-mr800 --max-allocs-per-node 100000` | **56.13ms(−1.9)** | **83.13ms(−2.2)** | 一致 | **14,096 / 9,592B** | 約 3.5 分 |
| M | `-mr800 --max-allocs-per-node 1000000` | 56.06ms(−2.0) | 83.00ms(−2.4) | 一致 | 13,960 / 9,295B | 約 15 分 |
| E | `-mr800 --allow-unsafe-read` | B と同じ | B と同じ | 一致 | — | — |
| C | `-mr800 --fomit-frame-pointer` | — | — | — | 常駐部が上限を 1.7KB 超え、地形モジュールだけでも 354B 超え | — |

- `--max-allocs-per-node` を上げると、レジスタの割り当てが良くなり、**速く、しかも小さく**なる。100,000 で頭打ちに近い
  (1,000,000 はコンパイルが 4 倍以上かかって 0.1ms しか変わらない)。
- `--fomit-frame-pointer` は、IX を使わない代わりに、スタック上の変数を毎回番地を計算してから読む形になり、
  コードが大きくなる(`rpt` で命令 102 → 133。結局 IY をフレームポインタの代わりに使っていた)。不採用。
- `--allow-unsafe-read` は効果なし。

## 4. 関数の属性

| 属性 | 結果 |
|---|---|
| `__preserves_regs(iyl, iyh)` | アセンブラの関数が IY を壊さないことを教えても、呼び出しの前後の `push iy` / `pop iy` は残った(このプロジェクトの 12 の宣言に付けて比べ、生成コードが同じ)。BC まで含めると減るが、`qmul` などは BC を壊すので付けられない |
| `static inline` | `rpt` を展開すると、四角形 1 枚あたりに実行する命令が約 477 → 約 208 になるが、コードは約 4 倍。地形モジュールに余裕がないので全部には使えない |
| `__z88dk_callee` / `__z88dk_fastcall` | 引数の渡し方を変えるだけで、スタックの枠(IX)の重さは変わらない |

## 5. C で書いた部分は、1 フレームの約 22%

ステージ 1 の 58.1ms のうち、C で書いた関数は 13.0ms(22%)、32 ビットのライブラリが 1.7ms(3%)、
アセンブラで書いた処理(辺・塗り・帯の管理・転送・投影の核など)が 43.3ms(75%)。ステージ 3 も同じ割合(C 18.6ms / 85.3ms)。

SDCC のオプションで縮められるのはこの C の部分だけで、D の −2ms は C の部分の約 15% に当たる。
**重さの大部分は、すでにアセンブラで書いた処理が受け持つ仕事の量(面・辺・行の数)と、転送で決まっている。**

> 計測の誤り(自分の): これまでのプロファイル(ステージ 1 で約 61ms)は、ライフを毎フレーム 8 に戻して被弾させ続けていたので、
> 宝の山の表の作り直し(`trolley_set_life`)が毎回のように動き、約 3ms 余分に入っていた。実際のプレイに近い条件(無敵)では約 58ms。

## 6. 結論

- `-mr800 --max-allocs-per-node 100000` は、絵を変えずに約 3.5%(ステージ 1 で −1.9ms)速く、コードも小さくなる。採る価値がある。
  代わりに、全体のビルドが約 1 分から約 3.5 分になる。
- それ以上は SDCC のオプションでは伸びない。C の部分が全体の 22% しかなく、SDCC の C はスタックの枠(IX)を使う形から変わらない。
- 30fps に近づけるには、アセンブラ側の仕事の量を減らす(飾りの点の投影をリングごとの事前計算にする、辺の準備を軽くする、
  遠くの飾りを描き分ける)ことが本筋。
