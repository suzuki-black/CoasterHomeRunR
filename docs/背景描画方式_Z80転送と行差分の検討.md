# Z80 モードでの転送と、行単位の差分転送 — 「転送タイミング検証結果への回答」3 章の検討

「転送タイミング検証結果への回答」が残した 2 つの実験（3.1 Z80 モードでの転送、3.2 行単位の差分転送）について。
3.1 は `make vdpbench` に項目を足すだけで測れたので、先に測った。

## 1. Z80 モードでの転送（3.1）

### 1.1 計測

vdpbench に次の項目を足した。

- BIOS の CHGCPU で Z80 モードに切り替え、表示中と垂直帰線中に、VRAM の空きへ 256 バイト書く
  - `OTIR` と、`OUTI` を 256 個並べた展開の 2 通り
- CHGCPU の往復（R800 → Z80 → R800）の時間

CHGCPU が要るので、実機の BIOS の機種（My_FS-A1ST_512K）だけで測った。C-BIOS の開発用機種は CHGCPU を持たない。

| 条件 | 1 バイトの時間 | 命令だけの時間（参考） |
|---|---|---|
| R800 `OTIR`（表示中・帰線中・画面オフ、前回の値） | 8.67µs | — |
| Z80 `OTIR` 表示中 | 6.86µs | 23T = 6.4µs |
| Z80 `OTIR` 垂直帰線中 | 6.84µs | 同上 |
| Z80 `OUTI` の展開 表示中 | **5.45µs** | 18T = 5.0µs |
| Z80 `OUTI` の展開 垂直帰線中 | **5.45µs** | 同上 |
| CHGCPU の往復 | **約 900µs** | — |

### 1.2 前提 3 つの判定

| 前提 | 結果 |
|---|---|
| Z80 モードでは S1990 の待ちが入らない | **成り立つ**。1 バイト 5.45µs で、ほぼ Z80 の命令の時間どおり（R800 の 8.67µs より 37% 速い）。表示中と帰線中の差も無い |
| CHGCPU の往復コストが無視できる | **ほぼ成り立つ**。往復 0.9ms |
| 転送中は R800 が止まり、それを差し引いても得になる | **成り立たない**（次の 1.3） |

### 1.3 成り立たない理由: 2 ブロックを 1 バイトに詰める計算が表に出る

いまの転送では、R800 が 2 ブロック（描画バッファの 2 バイト）を 1 バイトに詰めながら送っている。詰める計算（約 20 サイクル）は
S1990 の 62 サイクルの待ちに隠れていて、時間がかかっていない（vdp.s の転送）。

Z80 に送らせる場合、Z80 は 3.58MHz なので、詰める計算まで Z80 にやらせると 1 バイト 18µs 前後になり、かえって遅い。
そのため詰める計算は R800 が先に済ませる必要があり、その分の時間が表に出る。

| 方式 | 詰める計算（R800） | 切り替え | 送る | 合計 |
|---|---|---|---|---|
| いま（R800 が詰めながら送る） | 待ちに隠れる | — | 1536B × 8.67µs = 13.3ms | **13.3ms** |
| Z80 で全部送る | 1536B × 約 20 サイクル ≒ 4.3ms | 0.9ms | 1536B × 5.45µs = 8.4ms | **約 13.6ms** |
| 同上、詰める計算を 15 サイクルまで削れた場合 | 約 3.2ms | 0.9ms | 8.4ms | **約 12.5ms** |

詰める計算の時間は、命令の数からの見積もりで、実測ではない。

- 良くて 0.8ms の短縮で、悪ければ遅くなる。
- Z80 で動く間は R800 も止まるので、ほかの処理を重ねることもできない。
- 帰線中と表示中で速さが変わらないので、「帰線中に Z80 で送り、残りを表示中に」という分け方にも意味がない。

再反論側の条件（「1 つでも崩れたら取り下げる」）どおり、**3.1 は取り下げ**とする。

描画バッファを最初から詰めた形（1 バイト = 横 2 ブロック）で持てば詰める計算は消える。ただしその場合、塗り（LD (HL),A の展開）が
奇数の端で半分のバイトを読み書きすることになり、塗りの 6.5ms が重くなる。転送の 4ms 程度を取るために描画全体を作り直す価値は無いと判断する。

### 1.4 わかったこと

ターボR の R800 は、VDP への書き込みだけは Z80 より遅い（R800 8.67µs、Z80 の OUTI の展開 5.45µs）。

ただし R800 の 62 サイクルの待ちが、丸ごと空いているわけではない。検証記録の「転送の待ち時間に塗りを実行する」の実験では、
空きは 1 バイトあたり 15〜25 サイクルで、詰め替えの計算でほぼ埋まっていた。この実験は main より遅くなったので保留にしている。
転送の時間を R800 の別の仕事に回す余地も、ほとんど残っていない。

## 2. 行単位の差分転送（3.2）

考え方に同意する。HUD 13 行の除外を実装するとき、「行ごとに送る・送らない」のフラグを持つ形にしておく。

比較の方法は、提案の「32 バイトそのもの、またはハッシュを面ごとに持つ」ではなく、描く側の情報を使うほうが安い。

- 空と遠い地面は 2 色の行塗りで描いている。行ごとに「1 色で塗った行か、その色は何か」を面ごとに覚えておけば、比較は 1 行 2 バイトで済む。
- 描画バッファは詰める前の 64 バイトなので、32 バイトの比較には、詰めた結果を面ごとに残しておく必要がある（RAM 3KB、比較 1 行 約 55µs）。

効く場面は限られる。

- コースターは坂や揺れでピッチが細かく変わり、地平線の行が毎フレーム動くことが多い。
- 空に飾り（観覧車・旗・アーチ）が入る行は対象にならない。
- 見込みは、屋外で地平線より上の数行（1 行 277µs、数行で 1ms 前後）。

優先順位は再反論側の案どおり、5 章の打ち手の後とする。

## 3. 優先順位（変更なし）

| 順位 | 打ち手 | 見込み |
|---|---|---|
| 1 | 帯の管理の作り直しの続き | 7.1 → 4〜5ms |
| 2 | HUD 13 行を転送しない（行ごとの送る・送らないのフラグで作る） | 転送 -3.6ms |
| 3 | 変換・投影の C の部分をアセンブラへ | 約 3ms |
| 4 | 飾りの描き分け、描画距離の調整 | 面数枚分 |
| 後 | 行単位の差分転送（2 の仕組みに乗せる） | 屋外で 1ms 前後 |
| 取り下げ | Z80 モードでの転送 | ±1ms 未満 |

## 4. 実機での確認

`make vdpbench` の ROM（`build/vdpb/TrolleyHomeRun_VDPBENCH [ASCII8].rom`）に Z80 の項目も出るようにした。

| 画面の表示 | 左の列 | 右の列 |
|---|---|---|
| DISP / VBL | R800 | Z80 の `OTIR` |
| OFF | R800 | CHGCPU の往復（µs） |
| ZOUTI | Z80 の `OUTI` の展開、表示中 | 同、帰線中 |

単位は 1 バイトの時間（0.01µs）。実機で R800 と Z80 の値の関係が openMSX と大きく違う場合は、ここに戻る。
