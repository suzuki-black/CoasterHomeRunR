# 検証記録

仕様書の【要検証】項目と、実装中に openMSX で測った結果・つまずきの記録（仕様書 9 章ルール 5）。
環境: openMSX 21 / 開発用機種 `TH_turboR_dev`（C-BIOS + turbo R のハード、RAM はスロット 3-0）。
**速度はエミュレータ参考値**。最終確認は実機（FS-A1ST / FS-A1GT）で行う。

## 起動・CPU・メモリ（M1）

| 項目 | 結果 |
|---|---|
| ASCII8 の起動 | bank0 のローダーが bank2-5 を RAM ページ1・2 へ写し、0x4000 のエンジンへ飛ぶ。先頭の印 `TH` を照合 |
| R800 DRAM | C-BIOS には CHGCPU が無いので、MSXVER<3 かつ S1990 ありのときだけ S1990 reg6 を直接 0 にする。読み返し `00`（R800 DRAM）を確認 |
| 実機ファーム | MSXVER>=3 なら CHGCPU(0180h, A=82h)。**未確認**（実機・実ファームのエミュで要確認） |
| 使うマッパーセグメント | 既定の 0-3 のみ（ページ0-3 の初期配置のまま）。DRAM モードの BIOS コピー域とは重ならない想定【要実機確認】 |
| RAM の配置 | 0x4000-0xBFFF コード（現在 約19KB）、0xC000-0xCBFF 描画バッファ、0xCC00- 変数（約2.3KB）、0xE0F0 スロット ID、0xE100-0xEE90 レール表 |

### つまずき: RAM を 3-2 に置いた機種では R800 が 2〜3 倍遅く測れる
最初は `CBIOS_turboR`（RAM がスロット 3-2）で測り、空ループ 1 周（11 命令）が 49 サイクルかかった。
openMSX の R800 はスロット 3-0 だけを内蔵 RAM としてウェイト無しで扱う（TurboRVoxelShooter の README にも同じ記録）。
RAM を 3-0 に移した `tools/openmsx/TH_turboR_dev.xml` で 17 サイクルになった。**速度を測るときは必ずこの機種で。**

### ROM 上で動くコードが無いか・DRAM モードか（make slotcheck）
エミュレータ時刻 10µs ごとに PC を読み、PC のあるページで選ばれているスロットで分類した。

| 場面 | カートリッジ | RAM(3-0) | BIOS |
|---|---|---|---|
| タイトル | 0% | 99.8% | 0.2% |
| ゲーム中 | 0% | 99.24% | 0.76% |

- S1990 レジスタ 6 = 00（R800・DRAM モード）
- BIOS の分は垂直帰線ごとの BIOS 割り込み処理（→ H.TIMI）。ゲーム中に BIOS を呼ぶ処理は無い
  （入力・PSG・VDP はポート直接）。開発用機種の C-BIOS は ROM だが、実機の DRAM モードでは BIOS も RAM 上のコピー
- カートリッジ上の実行は起動時のローダー（バンク0）だけ。ステージの読み込みもページ3の常駐ローダーで行い、
  ROM から読むのはデータだけ
- 実機ファームでの CHGCPU(0180h, A=82h)経路: **WebMSX（ターボR・実機ファーム）で確認済み**（2026-09-27、ユーザー計測）。
  計測用 ROM のタイトルに `CPU:R800 DRAM`、ゲームは最後まで動作（ページ0の RAM 化・ステージ読み込みも実機ファーム上で問題なし）

### ページ0を自前の RAM に（空き領域の拡大）
ゲーム中は BIOS を呼ばないので、初期化後にページ0をマッパーの空きセグメント（4）に切り替え、
0x0038 に自前の割り込み処理を置いた。塗りの展開ブロックと辺キャッシュ（計 6.3KB）をページ0へ移し、
エンジンのコード上限を 23.3KB → 29.7KB に広げた（ページ0にはさらに約 9.5KB の空き）。
- BIOS が要るのはステージの読み込み（ENASLT）だけ。常駐ローダーがその間だけページ0を BIOS に戻す
  （基本スロットのレジスタだけ戻せばよい。実機の BIOS はスロット 0-0 だが、スロット 0 側の拡張スロットのレジスタには触らない）
- 実行は 100% RAM 上になった（make slotcheck）。C-BIOS の割り込み処理（ROM 上、キーボード走査つき）を毎フレーム通らなくなり
  20.1 → 20.9fps
- 計測のつまずき: 何もしない計測ではやられてゲームオーバー画面（軽い）が平均に混ざり、23fps と高く出ていた。
  make perf は計測中ライフを減らさず、場面が変わっていないかも出す

### ステージデータの ROM バンク読み込み（仕様書 7.3）
- ステージは C の定数だけで書き、読み込み先 0xB400 に合わせて単独でリンク（src/stage/）。先頭 2 バイトが Stage へのポインタ
- tools/mkrom.py が指定バンク（ステージ 1 はバンク 6）に置く。3KB（0x9C00-0xA7FF）を超えたらビルドエラー
- 常駐ローダー（0xE000）が割り込みを止め、ENASLT でページ1をカートリッジにして bank / bank+1 を窓に出し、
  LDIR で写してからページ1を RAM に戻す
- 読み込み先は 0xB400-0xBFFF（3KB）。辺キャッシュはフレームごとの先着割り当て（96 本）にしてページ0へ

| 項目 | 結果 |
|---|---|

### 試して捨てた: ストリーム転送（描画の裏で 1 バイトずつ送る）
描画バッファを 2 面にし、前のフレームを描画中の各所（乗算・割り算・行ループ）から 1 バイトずつ送る方式を試した。
1 バイト送る処理（その場でのパック込み）が約 40 サイクルかかり、VDP の待ち 62 サイクルとほぼ同じなので、
**かえって遅くなった**（4 ティック/フレーム）。送信口が足りない区間も多かった（1 フレームで 441 回）。まとめて転送に戻した。

## 3D 描画（M3）

| 項目 | 結果（前向き・洞窟） |
|---|---|
| フレームレート | **12〜16fps**（目標 30fps に未達） |
| 1 フレームの内訳 | 環境 約41ms（うち 多角形 26 枚の塗り 26ms）、転送 13.5ms、敵・HUD・トロッコ 約5ms |
| 多角形 1 枚 | 約 1.0ms（辺 1 本 157µs × 約3.5、スパン塗り 226µs、準備 約240µs） |
| MULUW | 動作確認済み（ED C3）。`fmul` 1 回 11.7µs（呼び出し込み） |

### 高速化でやったこと（効果の大きい順）
1. RAM をスロット 3-0 へ（上記、2〜3 倍）
2. 投影・辺の計算・スパン塗りをアセンブラへ（C の `edge()` は 1 本 約270 行の IX 相対コードだった）
3. リングの頂点を 1 フレーム 1 回だけ投影してキャッシュ（投影 181 回 → 約40 回）
4. カメラを含む区間は、0.6m 先の「仮リング」から描く（頂点が全部画面外に出るのでニアクリップ不要）
5. 奥の開口部を黒い六角形で塞いでバッファの全消去をやめる
6. 12m より先の区間は「リングの六角形 1 枚」で近似（面 6 枚 → 1 枚）
7. 辺の傾きの割り算を 9bit 仮数の逆数表 + MULUW に、開始位置を傾き × 行数に（割り算 3 回 → 0 回）

### つまずき: 番兵値で外接矩形の比較が壊れ、多角形のほとんどが捨てられていた
`sbc hl,de` の符号で比較する前提（差が 16bit に収まる）なのに、最小・最大の初期値に 0x7FFF / 0x8000 を使っていた。
差があふれて比較が逆になり、多角形の大半が「画面外」扱いに。**見かけ上とても速く測れていた**。
最初の頂点で初期化して直した。**速くなったときほど画面（バッファのダンプ）を確認する。**

### R800 のメモリアクセスのコスト（openMSX、RAM 3-0）
BENCH=1 のベンチで測った（1 回あたり、呼び出しの手間込み）:

| 64 回の繰り返し | サイクル | 1 回あたり |
|---|---|---|
| `nop` | 122 | 約 1.5 |
| `ld (hl),a` / `inc l`（描画バッファへ） | 420 | 約 6 |
| `push bc`（2 バイトずつ） | 297 | 約 4.6（1 バイト 2.3） |

コードと別のページのデータに触れるたびに 3〜4 サイクルかかる。**変数をメモリに置いて出し入れするほど遅い**ので、
ホットパスは値をレジスタに持ったまま回す。C（SDCC）の IX 相対のフレーム変数は特に重い。

### 計測の道具
- `make perf`: 条件をそろえた平均 fps と、関数ごとの時間（呼び出し〜戻り）
- `make pcprof`: エミュレータ時刻 10µs ごとに PC を読む統計プロファイル。ローカルラベル単位で重い場所が分かる
  （関数ごとの計測では C の `ring_make` のループ 1 か所で 6% を食っているのが見えなかった）

塗りの自己書き換えで「色を入れる命令」を飛ばす誤りがあり、画面が崩れたまま速度だけ測っていた。

### 試して保留: 転送の待ち時間に塗りを実行する（ブランチ exp/fused-xfer）
描画バッファを 2 面にし、3D の塗りを「予約リスト」に積んで、前のフレームの転送ループの中で 1 バイト送るごとに
裏レジスタで実行した。結果は 17.3fps で **main より遅かった**。
- 転送ループの空き時間は、1 バイトあたり NOP 10〜15 個分（約 15〜25 サイクル）しかなかった。
  詰め替えなしの `outi` だけの転送でも NOP 20 個で転送が伸び始める（62 サイクル丸ごとが空くわけではない）
- 予約を積む処理（行ごとの位置と幅）が、塗りそのものとほぼ同じ重さだった

## VDP への書き込みの速さ: 表示中・垂直帰線中・画面オフ・50Hz(2026-10-01、make vdpbench)

「垂直帰線中や画面オフなら VDP への OUT が速くなるのでは」という提案を確かめた。VRAM の空きへ OTIR で 256 バイト書き、
システムタイマで測った(src/engine/vdpbench.c。結果は画面に出るので WebMSX・実機でも同じ ROM で測れる)。

| 条件 | TH_turboR_dev | My_FS-A1ST_512K(実機の BIOS) |
|---|---|---|
| 表示中 | 8.67µs/B | 8.67µs/B |
| 垂直帰線中 | 8.67µs/B | 8.67µs/B |
| 画面オフ | 8.69µs/B | 8.67µs/B |
| 垂直帰線の長さ 60Hz / 50Hz | 4,376µs / 6,113µs | 4,376µs / 6,109µs |
| 帰線中に書ける見込み 60Hz / 50Hz | 504B / 704B | 505B / 704B |

**どの条件でも同じ**。待ちは VDP の表示期間の制約ではなく、ターボR(S1990)が R800 からの VDP アクセスに一律に入れるもの(openMSX の再現)。
転送は「何バイト送るか」でしか縮まない。実機での確認は ROM カートリッジが届いてから同じ ROM で行う。

> 計測で詰まった点: vdp_wreg / vdp_set_write は最後に ei する。計測中にこれを使うと、S#2 を読むために R#15 = 2 にしている
> 最中に割り込みが入り、割り込み処理が S#0 の代わりに S#2 を読んで割り込みが解除されず、割り込みが入り続けて止まった。
> 計測中は割り込みを止めたまま書く専用の処理を使う。

### Z80 モードでの書き込み(2026-10-01、make vdpbench、My_FS-A1ST_512K だけ。CHGCPU が要るため)

| 条件 | 1 バイトの時間 |
|---|---|

| Z80 `OUTI` の展開 表示中 / 垂直帰線中 | **5.45µs / 5.45µs** |
| CHGCPU の往復(R800 → Z80 → R800) | 約 900µs |

Z80 には S1990 の待ちが入らず、命令の時間どおりに書ける(R800 の 8.67µs より速い)。表示中と帰線中の差は無い。

## 飾りの四角形を長方形で塗る(2026-10-03)

### 重かった理由
リング面の飾り(遊園地のテント・柱・アーチ、森の幹と葉、町の家の壁など)は、すべて「リングの中心 + (u, v) × 拡大率」の点で作り、
四角形は C の `rquad` → 点ごとの `rpt`(C)→ 多角形の塗り(raster:外接矩形・辺 4 本・行ごとの左右端)で描いていた。
- `rpt` は掛け算 2 回と足し算だけだが、C の関数呼び出し(スタック渡しの引数、IX の枠、退避)で 1 フレーム 4〜5ms かかっていた
- リング面の形は画面上でそのまま縮小されるだけなので、`rquad` は**画面上では必ず軸に沿った長方形**。それを汎用の多角形の塗りに通し、
  縦の 2 辺を 1 本 約 840 サイクルかけて計算していた。角の計算も、u・v の 2 通りずつなのに 8 回掛けていた

### 直したこと
- raster.s に `rquad_a`(長方形)と `rpt_a`(点)を足す。引数はスタックでなく変数で渡す(env.c のマクロ `RQUAD` / `RPT`)
- `rquad_a` は掛け算 4 回で長方形を求め、raster と同じ丸め(列 = (x + 8) >> 4、行 = (y + 7) >> 4、画面に収める)で rect_fill に渡す。
  丸めは辺の速い経路・遅い経路・画面外の扱いを読んで合わせた

組(列ペア 1 つ × 8 行 = パターン 1 つ、VRAM で連続する 8 バイト)の 7〜8 割は変わらない。どの帯(8 行)でも同じくらい変わらない。

### 作り(vdp.s の xfer_prep / vdp_xfer)
- ページごとに、最後に送った中身の写しを持ち、組ごとに比べて、変わった組の続き(区間)だけを送る。
- 写しを別の表に置いて 1 バイトずつ比べる版(1 版目)は、比べるだけでステージ 1 で約 2.5ms かかった。
  R800 はアクセスする 256 バイトのページが変わるたびに待たされ、1 バイトごとに「コード → 写し → コード → 描画バッファ」と行き来するため。
- 2 版目から、写しを**比べるコードの即値**として持つ。組ごとに「pop hl / ld de, #写し / sbc hl, de / jp nz, 後始末」を 4 回(36 バイト)。
  SP を描画バッファに向けて(割り込みを止めて)頭から走らせる。写しの読み込みは命令の取り込みになり、比べるのは 1 組 約 52 サイクル。
- 3 版目で、組ごとの後始末(写しの即値の書き換えと、変わった組の番号を表に書く)を、番地を埋め込んだ組ごとのコードにした
  (番号や番地の計算・掛け算が無くなる)。比べるコードと後始末で 1 ページ約 13KB になるので、ページ 0 用をマッパーのセグメント 6、
  ページ 1 用をセグメント 7 に置き、比べる間だけページ2に出す。
- 比べたあと、変わった組の番号の並びから区間を作り、区間ごとに「書き込み先を付け直す(OUT 2 回)→ ld hl, 番地 → OUTI の列へ call」の
  コードを 0xC800 に書き出す。書き出したコードは R800 でも Z80 でも動く。区間が 60 に達したら、残りを 1 つの区間で送る(コードは 1KB に収まる)。
- 送る組が 20 以上なら Z80 に切り替えて送る。見積もり(1 バイトで 3.22µs 速く、切り替えの往復 922µs)では 36 組が境目だったが、
  測ると 20 組が一番速かった(下の表)。

## 確かめたこと: 変数をコードと同じ 256 バイトのページに置いても速くならない(openMSX、2026-10-06)

## 試してやめたこと: R800 のまま、OUT の待ちの間に比べながら送る(2026-10-06)

## SCREEN 3(192 行)で、走査線割込みが来る行(2026-10-10)

誘導弾の「FIRE」の声を、ゲームを止めずに PCM で鳴らすための下調べ。ターボ R の PCM は CPU が 1 サンプルずつ書くしかなく、
割込みを出す時計も無いので、走査線割込みで 1 サンプルずつ出す(ZeroNoHoukouR の docs/PCM調査_2026-10-07.md と同じ方式)。
ZeroNoHoukouR は 212 行の画面で調べてあり、192 行の画面では割込みが来ない行に張って固まったため、192 行では PCM を鳴らしていない。
そこで、192 行の画面で R#19 の値ごとに割込みが来るかを測る検証 ROM を作った(tools/lineirq192/。build.sh で build/LINEIRQ.ROM)。

測り方: R800、SCREEN 3、IM1(BIOS の割込み処理から H.KEYI)。R#15 は普段から 1(BIOS が読む 0x99 が S#1 になり FH が落ちる)、
VBLANK 割込み(IE0)は切る。値 v ごとに 4 フレーム、0 行目の割込みで時刻を取ってから v を張り、v の割込みまでの時間を
システムタイマ(1 カウント 3.911µs)で測った。openMSX の My_FS-A1ST_512K。

| R#19 の値 | 結果 |
|---|---|
| 2〜234 | 来る。0 行目から値の行数ぶん後(1 行 ≒ 16.25 カウント = 63.6µs。例: 100 → 1,629 カウント) |
| 0・1 | 0 行目の割込みの中で張ると過ぎているので、次のフレーム(4,267〜4,282 カウント) |
| 235〜255 | 来ない |

1 フレームは 262 行(4,267 カウント)。割込みが来ないのは 235〜261 行目の 27 行(約 1.7ms)で、212 行の画面の 17 行(約 1.1ms)より長い。

## SCREEN 3 で、走査線割込みから PCM の声を止めずに鳴らす(検証 ROM、2026-10-10)

検証 ROM(tools/lineirq192/pcmtest.s。build.sh で build/PCMTEST.ROM ほか、測り方は pcmrec.tcl)で、mac の読み上げで作った
「Fire!」(0.41 秒、1,645 サンプル、3,996Hz・8bit)を、メインを止めずに鳴らした。openMSX の My_FS-A1ST_512K。

作り: R800(DRAM モード。プログラムと声は RAM に写して動かす)、SCREEN 3、IM2(BIOS を通さない)、R#15 は普段から 1、IE0 は切る。
鳴っていない間は 2 行目に割込みを張って基準の時刻 TA を取り、鳴らし始めもそこから。張った行の割込みが来たら 1 サンプル出し
(A5h = 03h のダブルバッファ)、次のサンプルの行を張る。行は 9.7 の固定小数点で 1 サンプル 3.9375 行ずつ、予定の時刻は 64 カウントずつ
進める(フレームの境目で行から時刻を出し直してそろえる)。割込みが来ない行(235〜261 と次のフレームの 0〜2 行)と、予定まで
8 カウントを切ったものは、割込みの中で時刻まで待って出す。1 行より遅れたサンプルは飛ばす(長さは変えない)。

結果(1 回目の声。間隔は A4h に書いた時刻の差、理想 64 カウント):
| | 間隔 | 飛ばした数 | 声の間にメインが回れた割合 |
|---|---|---|---|
| 割込みを止めない | 46〜84(48〜80 に 99.5%) | 0 | 64%(時刻の記録あり)/ 68%(なし) |
| 毎フレーム 2.5ms 割込みを止める | 46〜706(止めた区間で 2.6〜2.8ms 空く) | 3 回で 224 | 61% |
| 遅れの判定を外した下限(止めない) | — | 0 | 72% |

- 声の間、割込みが CPU の約 3 割を使う。うち約 11.5% は割込みが来ない 30 行の待ち、残りが割込み 1 回(約 40〜50µs)。
  R800 の DRAM モードではメモリの読み書きのたびに待ちが入り、割込み 1 回の 150 命令ほどでこれくらいになる。
- 毎フレーム割込みを止める区間があると、その間のサンプルは出せない(ゲームでは転送の前の比較が最大 2.5ms 止める)。
- つまずいたこと(どれも検証 ROM の作りの誤り):
  - 待って出す範囲(80 カウント)をサンプルの間隔(64)より広くし、声の間じゅう割込みの中で待ち続けた(メインが止まった)。
  - 割込みのたびにタイマを読んで行を割り算で出していて遅く、張る行を過ぎて 1 フレーム止まった。
  - 行を 8.8 で持ち、次のフレームの頭(262 行以上)で 16bit を超えた。張る行が 235 以上かを、切り捨ての行で判定していた。
    262 行の手前を 2 倍して 16bit を超え、小さい行に見えた。時刻を出すずらしを符号つきにして、260 行目あたりを負に読んだ。
  - プログラムを ROM の上で動かしていて、割込みの重さを大きく見積もった(R800 は ROM を読むたびに待たされる)。
  - Tcl の `after time 0.4 [list set x [cnt]]` で、[cnt] が登録時に評価された(グローバルの CLAUDE.md の落とし穴)。

## ゲームの中で「FIRE」を止めずに鳴らす(手順 1、2026-10-10)

検証 ROM の方式(待たない版)をゲームに入れた(src/engine/pcm.s。声のデータは src/engine/voice_fire.s を tools/gen_voice.sh で作る)。
ふだんは今までどおり垂直帰線の割込み。pcm_fire で頼まれると、次の垂直帰線の割込みの中で R#15 = 1・IE0 を切る・IE1 を立てるに切り替え、

「合図」を張り、毎フレームの処理(htimi)をして次のフレームの 3 行目から続ける。出し終わったら次の合図で戻す。
(調べ用)g_dbg_fire に 1 を書くと、ゲームの毎フレームの処理が鳴らす。

入れる途中で見つけて直したこと(どれも openMSX で A4h への書き込み・割込み・FH・IFF を時刻つきで記録して見つけた):

  声の間は Z80 に切り替えず、R800 のまま送る(vdp.s の vdp_xfer)。

## 声を鳴らしている間は、転送の前の比較を 8 組ごとに区切って割込みを受ける(手順 2、2026-10-10)

転送の前の比較(vdp.s の xfer_prep)は、SP を描画バッファに向けて pop で読むので、割込みを止めて約 2.2ms 走る。声の間は、
その間のサンプルが出せず、1 回の声に 1 回 3ms 前後止まっていた。声を鳴らしている間だけ、比べるコードの 8 組ごとの組の頭(23 か所)の
3 バイトを「jp xp_brk」に書き換えておき(元の 3 バイトは表に覚える)、xp_brk でふつうのスタックに戻して一瞬だけ割込みを受け、
3 バイトを書き戻してその組から続ける(スタックは使わない。割込みを止める 1 回は約 0.09ms)。

あわせて直したこと:
- 来ない行(235)を張って、声の形のまま割込みが来ず、毎フレームの処理も止まって固まった(声を 40 フレームごとに鳴らしながら絵を

  235 になった。行を張る所で 234 より後の行は張らず合図の行にし、次のフレームの最初の行が 230 を超えたら 3 行目にする。
- 遅れの見積もりが大きくなったのは、2 行ほどの遅れを遅れと見なさず(境目 40 カウント)、そのまま次の行を張って、張り終える前に
  過ぎたため。境目を 24 カウント(約 1.5 行)にした。区切りを 16 組ごとにしたときは、1 回約 3 行遅れることがあった。

12m より先の飾りを描かないと -1.9ms(飾りはもともと「角だけ投影してまっすぐな長方形で塗る」形で、残るのは部品の数だけ)。

敵の部品(1/16m 単位の矩形)は、幅か高さが (z - 1) >> 10 以下なら描かない(当たり判定にも足さない。geom.s の g_dm_thin)。
これは画面で半ブロックに満たない部品で、もとから四捨五入で 1 ブロック出たり消えたりしていた(目・槍・杖・角など)。
縁取りの回と次の回で同じに決まるので、座標の表はずれない。

| 効かせる範囲 | 1 フレーム | 差 |
|---|---|---|
| どの距離でも(4m より先) | 53.81ms | -1.25ms |
| 12m より先 | 54.47ms | -0.59ms |
| 12m より先、アイテム(救急箱・誘導弾の箱・宝箱)は除く(採用) | 54.58ms | -0.48ms |

アイテムは遠くでも十字や弾の色で見分けられるように除いた。

それによる自動ロックの出方のずれだけ(ステージ 1・2・振り向き・タイトルは全フレーム一致)。

## 重ね塗りの計測と、試してやめたこと: 空と地面を見えうる所だけ塗る(2026-10-11)

ほかの 3D の軽量化の手法を調べた(Doom の solidsegs、Quake の sorted spans など。手前から奥へ描き、塗った所を塗らない)。
効くかを先に見るため、描画バッファへの書き込みのうち、同じフレームで後から上書きされた分を数えた(tools/overdraw.tcl、
make overdraw STAGE=n。無敵・撃たない、フレーム 60〜900 の 20 フレームおき 43 枚、バイト単位)。

| ステージ | 書き込み | 上書きされた分 | うち空と地面の塗り | うち乗り物の下に描いた地形 |
|---|---|---|---|---|
| 1 | 2559 | 1023(40%) | 714 | 320 |
| 3 森 | 4053 | 2517(62%) | 1487(全面の 97%) | 320 |
| 4 町 | 3732 | 2196(59%) | 1059 以上 | 317 |

- 乗り物の絵は、丸ごと不透明な行が前向きで 2 行(41・43 行目)、後ろ向きで 0 行なので、その下を描かないことで減らせる分はわずか。
- 森の空と地面(1 フレーム約 1.1ms、push で全面)を、見えうる所だけ塗る形を試した。森の断面は天井の面だけが開いているので、
  見えうるのは「各区間の天井の隙間」と「一番奥のリングの穴」だけ。それぞれの外接矩形を 1 ブロック広げた範囲を行ごとにまとめ、
  その中だけを長方形で塗った(仮リングを先に作る。前だけを見ていて、リングがどれも森で 6 頂点とも手前のときだけ)。
  絵は VRAM で全フレーム一致したが、ステージ 3 で 54.40ms → 57.36ms と遅くなった。空の塗りは -1.0ms だったが、
  範囲を作る処理(C)が +2.3ms、範囲だけの長方形の塗りが +0.8ms。天井の隙間はカメラの近くで画面の上半分ほどに広がるので、
  外接矩形では塗る量があまり減らず、push で全面を塗るほうが速い。範囲作りをアセンブラにしても得は 0.2ms ほどと見て、戻した。

## 敵の更新は、写しを番地で直接触る(2026-10-11)

調べた手法のうち「遠くの敵の更新を 2 フレームに 1 回にする」は、このゲームが時間ではなく 1 フレームに 1 歩で進むので、
攻撃の間合いやタイマーまで変わる(2 歩ずつ進めると攻撃のフレームがずれうる)。先に update_enemy 自体を見た。
C のままで、ポインタ e のフィールドを IX の相対で何度も読み直していた(ステージ 3 で 2.77% + move_enemy 0.68% + attack 0.41%)。

更新する敵を作業用の写し g_ce に写し(カメラ座標 c を除く頭の 19 バイト。aimhit.s の ce_load / ce_store、LDI を並べる)、
update_enemy・move_enemy・attack・lunge・shoot は g_ce を番地で直接触り、終わったら書き戻す。動きは同じ。
ステージ 3 で 1 フレーム 54.40ms → 54.08ms、コードは 805 バイト小さくなった。絵はステージ 1〜5・振り向き・タイトルで全フレーム一致。
- 写すのに memcpy(LDIR、25 バイト)を使うと、写す手間が 0.78% かかった(R800 の LDIR は 1 バイト 7 サイクル)。
- 種類の表(edef)も写しにしてみたが、写す手間で相殺された(54.08 → 54.10ms)。戻した。
- 自動で遊ぶ流れのテストは 0.1 秒ごとの時刻で操作するので、1 フレームの重さが変わると得点もわずかに変わる(105800 → 104800)。
