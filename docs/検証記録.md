# 検証記録

仕様書の【要検証】項目と、実装中に openMSX で測った結果・つまずきの記録（仕様書 9 章ルール 5）。
環境: openMSX 21 / 開発用機種 `TH_turboR_dev`（C-BIOS + turbo R のハード、RAM はスロット 3-0）。
**速度はエミュレータ参考値**。最終確認は実機（FS-A1ST / FS-A1GT）で行う。

## 起動・CPU・メモリ（M1）

| 項目 | 結果 |
|---|---|
| ASCII8 の起動 | bank0 のローダーが bank2-5 を RAM ページ1・2 へ写し、0x4000 のエンジンへ飛ぶ。先頭の印 `TH` を照合 |
| R800 DRAM | C-BIOS には CHGCPU が無いので、MSXVER<3 かつ S1990 ありのときだけ S1990 reg6 を直接 0 にする。読み返し `00`（R800 DRAM）を確認 |
| 実機ファーム | MSXVER>=3 なら CHGCPU(0180h, A=82h)。**未確認**（実機・実ファームのエミュで要確認） |
| 使うマッパーセグメント | 既定の 0-3 のみ（ページ0-3 の初期配置のまま）。DRAM モードの BIOS コピー域とは重ならない想定【要実機確認】 |
| RAM の配置 | 0x4000-0xBFFF コード（現在 約19KB）、0xC000-0xCBFF 描画バッファ、0xCC00- 変数（約2.3KB）、0xE0F0 スロット ID、0xE100-0xEE90 レール表 |

### つまずき: RAM を 3-2 に置いた機種では R800 が 2〜3 倍遅く測れる
最初は `CBIOS_turboR`（RAM がスロット 3-2）で測り、空ループ 1 周（11 命令）が 49 サイクルかかった。
openMSX の R800 はスロット 3-0 だけを内蔵 RAM としてウェイト無しで扱う（TurboRVoxelShooter の README にも同じ記録）。
RAM を 3-0 に移した `tools/openmsx/TH_turboR_dev.xml` で 17 サイクルになった。**速度を測るときは必ずこの機種で。**

### ROM 上で動くコードが無いか・DRAM モードか（make slotcheck）
エミュレータ時刻 10µs ごとに PC を読み、PC のあるページで選ばれているスロットで分類した。

| 場面 | カートリッジ | RAM(3-0) | BIOS |
|---|---|---|---|
| タイトル | 0% | 99.8% | 0.2% |
| ゲーム中 | 0% | 99.24% | 0.76% |

- S1990 レジスタ 6 = 00（R800・DRAM モード）
- BIOS の分は垂直帰線ごとの BIOS 割り込み処理（→ H.TIMI）。ゲーム中に BIOS を呼ぶ処理は無い
  （入力・PSG・VDP はポート直接）。開発用機種の C-BIOS は ROM だが、実機の DRAM モードでは BIOS も RAM 上のコピー
- カートリッジ上の実行は起動時のローダー（バンク0）だけ。ステージの読み込みもページ3の常駐ローダーで行い、
  ROM から読むのはデータだけ
- 実機ファームでの CHGCPU(0180h, A=82h)経路: **WebMSX（ターボR・実機ファーム）で確認済み**（2026-09-27、ユーザー計測）。
  計測用 ROM のタイトルに `CPU:R800 DRAM`、ゲームは最後まで動作（ページ0の RAM 化・ステージ読み込みも実機ファーム上で問題なし）

### ページ0を自前の RAM に（空き領域の拡大）
ゲーム中は BIOS を呼ばないので、初期化後にページ0をマッパーの空きセグメント（4）に切り替え、
0x0038 に自前の割り込み処理を置いた。塗りの展開ブロックと辺キャッシュ（計 6.3KB）をページ0へ移し、
エンジンのコード上限を 23.3KB → 29.7KB に広げた（ページ0にはさらに約 9.5KB の空き）。
- BIOS が要るのはステージの読み込み（ENASLT）だけ。常駐ローダーがその間だけページ0を BIOS に戻す
  （基本スロットのレジスタだけ戻せばよい。実機の BIOS はスロット 0-0 だが、スロット 0 側の拡張スロットのレジスタには触らない）
- 実行は 100% RAM 上になった（make slotcheck）。C-BIOS の割り込み処理（ROM 上、キーボード走査つき）を毎フレーム通らなくなり
  20.1 → 20.9fps
- 計測のつまずき: 何もしない計測ではやられてゲームオーバー画面（軽い）が平均に混ざり、23fps と高く出ていた。
  make perf は計測中ライフを減らさず、場面が変わっていないかも出す

### ステージデータの ROM バンク読み込み（仕様書 7.3）
- ステージは C の定数だけで書き、読み込み先 0xB400 に合わせて単独でリンク（src/stage/）。先頭 2 バイトが Stage へのポインタ
- tools/mkrom.py が指定バンク（ステージ 1 はバンク 6）に置く。3KB（0x9C00-0xA7FF）を超えたらビルドエラー
- 常駐ローダー（0xE000）が割り込みを止め、ENASLT でページ1をカートリッジにして bank / bank+1 を窓に出し、
  LDIR で写してからページ1を RAM に戻す
- 読み込み先は 0xB400-0xBFFF（3KB）。辺キャッシュはフレームごとの先着割り当て（96 本）にしてページ0へ

| 項目 | 結果 |
|---|---|
| VRAM マップ（仕様書 7.4） | 仕様どおりで動作。R#4 = 0/1 でパターンジェネレータ A/B を切替 |

### 試して捨てた: ストリーム転送（描画の裏で 1 バイトずつ送る）
描画バッファを 2 面にし、前のフレームを描画中の各所（乗算・割り算・行ループ）から 1 バイトずつ送る方式を試した。
1 バイト送る処理（その場でのパック込み）が約 40 サイクルかかり、VDP の待ち 62 サイクルとほぼ同じなので、
**かえって遅くなった**（4 ティック/フレーム）。送信口が足りない区間も多かった（1 フレームで 441 回）。まとめて転送に戻した。

## 3D 描画（M3）

| 項目 | 結果（前向き・洞窟） |
|---|---|
| フレームレート | **12〜16fps**（目標 30fps に未達） |
| 1 フレームの内訳 | 環境 約41ms（うち 多角形 26 枚の塗り 26ms）、転送 13.5ms、敵・HUD・トロッコ 約5ms |
| 多角形 1 枚 | 約 1.0ms（辺 1 本 157µs × 約3.5、スパン塗り 226µs、準備 約240µs） |
| MULUW | 動作確認済み（ED C3）。`fmul` 1 回 11.7µs（呼び出し込み） |

### 高速化でやったこと（効果の大きい順）
1. RAM をスロット 3-0 へ（上記、2〜3 倍）
2. 投影・辺の計算・スパン塗りをアセンブラへ（C の `edge()` は 1 本 約270 行の IX 相対コードだった）
3. リングの頂点を 1 フレーム 1 回だけ投影してキャッシュ（投影 181 回 → 約40 回）
4. カメラを含む区間は、0.6m 先の「仮リング」から描く（頂点が全部画面外に出るのでニアクリップ不要）
5. 奥の開口部を黒い六角形で塞いでバッファの全消去をやめる
6. 12m より先の区間は「リングの六角形 1 枚」で近似（面 6 枚 → 1 枚）
7. 辺の傾きの割り算を 9bit 仮数の逆数表 + MULUW に、開始位置を傾き × 行数に（割り算 3 回 → 0 回）

### つまずき: 番兵値で外接矩形の比較が壊れ、多角形のほとんどが捨てられていた
`sbc hl,de` の符号で比較する前提（差が 16bit に収まる）なのに、最小・最大の初期値に 0x7FFF / 0x8000 を使っていた。
差があふれて比較が逆になり、多角形の大半が「画面外」扱いに。**見かけ上とても速く測れていた**。
最初の頂点で初期化して直した。**速くなったときほど画面（バッファのダンプ）を確認する。**

### R800 のメモリアクセスのコスト（openMSX、RAM 3-0）
BENCH=1 のベンチで測った（1 回あたり、呼び出しの手間込み）:

| 64 回の繰り返し | サイクル | 1 回あたり |
|---|---|---|
| `nop` | 122 | 約 1.5 |
| `ld (hl),a` / `inc l`（描画バッファへ） | 420 | 約 6 |
| `push bc`（2 バイトずつ） | 297 | 約 4.6（1 バイト 2.3） |

コードと別のページのデータに触れるたびに 3〜4 サイクルかかる。**変数をメモリに置いて出し入れするほど遅い**ので、
ホットパスは値をレジスタに持ったまま回す。C（SDCC）の IX 相対のフレーム変数は特に重い。

### 計測の道具
- `make perf`: 条件をそろえた平均 fps と、関数ごとの時間（呼び出し〜戻り）
- `make pcprof`: エミュレータ時刻 10µs ごとに PC を読む統計プロファイル。ローカルラベル単位で重い場所が分かる
  （関数ごとの計測では C の `ring_make` のループ 1 か所で 6% を食っているのが見えなかった）

### 3 回目（17.6 → 17.9fps）
| 対策 | 効果 |

塗りの自己書き換えで「色を入れる命令」を飛ばす誤りがあり、画面が崩れたまま速度だけ測っていた。

### 試して保留: 転送の待ち時間に塗りを実行する（ブランチ exp/fused-xfer）
描画バッファを 2 面にし、3D の塗りを「予約リスト」に積んで、前のフレームの転送ループの中で 1 バイト送るごとに
裏レジスタで実行した。結果は 17.3fps で **main より遅かった**。
- 転送ループの空き時間は、1 バイトあたり NOP 10〜15 個分（約 15〜25 サイクル）しかなかった。
  詰め替えなしの `outi` だけの転送でも NOP 20 個で転送が伸び始める（62 サイクル丸ごとが空くわけではない）
- 予約を積む処理（行ごとの位置と幅）が、塗りそのものとほぼ同じ重さだった

## VDP への書き込みの速さ: 表示中・垂直帰線中・画面オフ・50Hz(2026-10-01、make vdpbench)

「垂直帰線中や画面オフなら VDP への OUT が速くなるのでは」という提案を確かめた。VRAM の空きへ OTIR で 256 バイト書き、
システムタイマで測った(src/engine/vdpbench.c。結果は画面に出るので WebMSX・実機でも同じ ROM で測れる)。

| 条件 | TH_turboR_dev | My_FS-A1ST_512K(実機の BIOS) |
|---|---|---|
| 表示中 | 8.67µs/B | 8.67µs/B |
| 垂直帰線中 | 8.67µs/B | 8.67µs/B |
| 画面オフ | 8.69µs/B | 8.67µs/B |
| 垂直帰線の長さ 60Hz / 50Hz | 4,376µs / 6,113µs | 4,376µs / 6,109µs |
| 帰線中に書ける見込み 60Hz / 50Hz | 504B / 704B | 505B / 704B |

**どの条件でも同じ**。待ちは VDP の表示期間の制約ではなく、ターボR(S1990)が R800 からの VDP アクセスに一律に入れるもの(openMSX の再現)。
転送は「何バイト送るか」でしか縮まない。実機での確認は ROM カートリッジが届いてから同じ ROM で行う。

> 計測で詰まった点: vdp_wreg / vdp_set_write は最後に ei する。計測中にこれを使うと、S#2 を読むために R#15 = 2 にしている
> 最中に割り込みが入り、割り込み処理が S#0 の代わりに S#2 を読んで割り込みが解除されず、割り込みが入り続けて止まった。
> 計測中は割り込みを止めたまま書く専用の処理を使う。

### Z80 モードでの書き込み(2026-10-01、make vdpbench、My_FS-A1ST_512K だけ。CHGCPU が要るため)

| 条件 | 1 バイトの時間 |
|---|---|
| Z80 `OTIR` 表示中 / 垂直帰線中 | 6.86µs / 6.84µs |
| Z80 `OUTI` の展開 表示中 / 垂直帰線中 | **5.45µs / 5.45µs** |
| CHGCPU の往復(R800 → Z80 → R800) | 約 900µs |

Z80 には S1990 の待ちが入らず、命令の時間どおりに書ける(R800 の 8.67µs より速い)。表示中と帰線中の差は無い。
ただし Z80 に送らせると、2 ブロックを 1 バイトに詰める計算(いまは R800 の待ちに隠れている)を R800 が先に済ませる必要がある
(約 3〜4ms)。それに切り替えの 0.9ms を足すと、いまの 13.3ms とほぼ同じになるので採らない
(docs/背景描画方式_Z80転送と行差分の検討.md)。

## 詰めたバッファ(1 バイト = 横 2 ブロック)への塗り(2026-10-02、make fillbench)

ゲーム中の塗り(fill)の呼び出しを記録し(tools/fillbench_log.tcl)、いまの fill と、詰めたバッファへ塗る pfill
(src/engine/fillbench.c)で再生して比べた(tools/fillbench_replay.tcl)。TH_turboR_dev、ステージ 1。

| 場面 | fill | pfill | 絵の食い違い |
|---|---|---|---|
| 開始 45 秒 | 3.96ms/フレーム | 4.30ms(+9%) | 0 |
| 開始 75 秒 | 4.97ms/フレーム | 5.62ms(+13%) | 0 |

- fill の時間の分解(R² 0.993): ブロック 1 つ 0.80µs(約 5.7 サイクル)、行 1 つ 約 11µs、呼び出し 1 回 7.6µs。
  ブロックを書く部分は塗りの約 4 割で、残りは行ごとの準備(tools/fillbench_stats.py)
- 1 フレームに 30 面、150〜210 行、1,760〜2,200 ブロック、奇数の端 140〜180 か所。幅 2 以下のスパンが 4 割
- Z80 の OUTI の展開で表示中に書いた 256 バイトを読み戻すと食い違い 0(openMSX の too_fast_vram_access = real、My_FS-A1ST_512K)
- BIOS の CHGCPU は戻るときに割り込みを許可する(切り替えの間は VDP の割り込みを止める必要がある)

塗りは悪化するが、Z80 転送で転送が約 4ms 縮むので全体では得になる見込み(docs/背景描画方式_詰めたバッファの計測.md)。

## 5 回目の高速化: 帯の管理(2026-10-03〜)

### 比べ方(新しい道具)
- ゲームの進みはフレーム単位で決まっている(位置・敵・スコアは、描画の速さが変わっても同じ番号のフレームで一致する)。
  そこで変更の前後を「同じ番号のフレーム」どうしで比べる。
- 絵: tools/frame_dump.tcl で同じ番号のフレームの描画バッファを書き出し、tools/frame_cmp.py で比べる。
  実時間のティック(g_tick)で決まるもの(電飾の点滅、被弾で飛び散る金貨の種)は、書き出すときにフレーム番号から決めた値へ差し替える。
  ライフもフレームごとに戻す(実時間で戻すと、戻すフレームがずれてコースターの壊れ具合がずれる)。
- 速さ: tools/perf_pos.tcl でレール上の位置ごとの 1 フレームの時間を取り、tools/perf_pos_cmp.py で同じ位置どうしを比べる。
- プロファイル: make pcprof を直した(タイトルを待つ、ページ0の塗り・ページ2のモジュールにも名前、関数ごとの集計)。

> つまずき: 比べる道具が実時間に左右されて、同じ絵なのに違うと出た(電飾の点滅・金貨の種・ライフを戻す時刻・数え始めのフレーム)。
> **比べる道具の出す「違い」は、まず道具を疑う。**

### 色 0 の面の辺を作らない
遊園地(屋外)では帯 1 本 6 面のうち 2 面が色 0(空なので塗らない)なのに、帯ごとに 18 本の辺をすべて用意していた
(1 フレーム 54 本のうち 14 本は使わない)。塗る面が使う辺だけを用意するようにした(raster.s の band_fast)。
6 面とも塗る帯(洞窟・坑道)は、確かめを飛ばして元と同じ処理を通る(確かめの分だけ遅くならないように)。

### 辺のスロットの用意と、行の x の写しを軽く
`slot_ensure`(新しく計算する辺 1 本の準備)は、入口から辺の計算に入るまで 333 サイクルかかっていた(ブレークポイントで実測)。

- 辺の計算(edge)が壊すのは IY だけなので、IX の退避をやめ、IY の退避は辺ごとから帯ごとに移す
- `seg_copy`: スロットは 64 境界なので見出しの番地を or で作り、push / pop をやめる(行数は裏の AF に置く。割り込み処理は裏レジスタを使わない)
