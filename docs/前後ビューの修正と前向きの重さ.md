# 前後ビューの修正と、前向きで増えた重さ

2026-11-02 のまとめ。

## 1. 前後ビューの矛盾(修正済み)

### 症状

1 面の最後のボスを倒したあと、前向きでは城が右に見える。ところが通り過ぎて振り向くと、城があった所に観覧車が見えた。

### 原因

地形の飾り(城・観覧車・テント・柵・家並み・鉄橋のトラスなど)は、リングの面の上で「中心 + (u, v) × q」の形で描いている。u は「レールの進む向きの右」を正とする。

後ろを向くと、レールの右は画面の左になる。ところが `rpt_a` / `rquad_a`(raster.s)は u をいつも画面の右として扱っていた。そのため後ろ向きのときは、全ステージで飾りが左右逆に描かれていた。城は左側の柵の陰に隠れ、反対側にあった観覧車が城の位置に見えていた。

敵は `rail_cam` で 3D のままカメラ空間へ変換しているので、前向きでも後ろ向きでも正しい側に出ていた。

### 直したこと

| 対象 | 内容 |
|---|---|
| 飾りの左右 | `g_u_neg`(視線が 90 度を越えたら 1)を見て、u の符号を反転する(raster.s の `rp_x`)。env.c の `ties_mid` も同じように直した |
| 遠景 | 山並み・運河の家並み・向こう岸・港を、一周 201 列の帯として、視線の向きに合わせて描く |
| 海 | 白波と小舟を世界に固定し、後ろ向きでは反転する(truss.s の `sw_back`) |
| 地平線の色 | 後ろだけを見ているときも、一番遠い屋外のリングで決める |
| 敵とアイテム | 通り過ぎても 20m 後ろまで残す(以前は約 3m で消えていた)。通り過ぎた弓兵は後ろからは撃たない |
| 誘導弾 | 撃った直後に振り向いても、飛び続けて当たる |

### 確かめたこと

- `make test`: PASS
- 6 面の自動プレイ(FS-A1ST、無敵): PASS、ボス 8 体
- 敵の枠の最大使用数: 7/14
- 敵が消える位置(3 面): 2.9m 後ろから 19.9m 後ろへ
- 撃った直後に振り向く(3 面): 修正前は弾だけ減り、敵は無傷。修正後は敵を倒す
- 全面の前向き・後ろ向きの画面を並べて見比べた

### 残っている点

- 振り向きの途中(45〜135 度)は、飾りの幅や位置が近似のままで、崩れて見える。
- 後ろにいる敵が撃った弾は、距離 3m の判定ですぐ消える(コードを読んだ限り)。直すと難易度が上がるので変えていない。

## 2. 今の問題: 前向きでも重くなった

### 数字

1 面を前向きのまま 30 秒走らせて測った(操作なし、My_FS-A1ST_512K)。

| ROM | 平均 | 1 フレーム |
|---|---|---|
| v0.1.1 | 24.42 fps | 40.9 ms |
| 前後ビューの修正版 | 24.23 fps | 41.3 ms |

6 面の自動プレイの平均 fps:

| 面 | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|
| v0.1.1 | 23.9 | 25.3 | 22.4 | 21.6 | 23.4 | 20.7 |
| 修正版 | 23.6 | 25.0 | 22.5 | 20.9 | 22.6 | 20.1 |

### 内訳の測り方

v0.1.1 と修正版について、上と同じ 30 秒の走りで CPU の PC を約 0.49ms ごとに記録した(約 6 万点)。記録した PC は、マッパーのページ 2 のセグメントと各モジュールの `.noi` で処理名に直した。raster.s / geom.s の内部ラベルは `.rst` から拾った。そのうえで、1 フレームあたりの時間を処理ごとに比べた。

| 処理 | v0.1.1 | 修正版 | 差 |
|---|---|---|---|
| `rp_x` | 0 | 0.230 ms | +0.230 ms |
| ほかの処理 | | | どれも ±0.07 ms 以内(記録のぶれの範囲) |

前向きで増えた分は、ほぼ `rp_x` で説明がつく。

### なぜ前向きでも増えるのか

`rp_x` は、飾りの点の画面の x を出すたびに呼ばれる。中では `g_u_neg` を読み、足すか引くかを分岐する。前を向いているときは答えが毎回「足す」なのに、確かめる手間(呼び出しと戻り、`g_u_neg` の読み出し、分岐)は点ごとにかかる。後ろ側を描いているわけではない。

20m 後ろまで残した敵の処理は、この 30 秒の測定でははっきりした増加として出なかった(差はぶれの範囲)。4〜6 面の自動プレイで fps が下がった原因の内訳は、まだ測っていない。

## 3. 試したことと、うまくいかなかったこと

### 測定の途中でつまずいたこと

- **既存の perf.tcl:** 0 フレームしか取れなかった。そこで、`g_perf_ticks` を 0.1 秒ごとに読むだけの fw.tcl を作って測り直した。
- **PC の記録の最初の集計:** `hex_fast` が増えたように見えた。実際は、`hex_fast` の後ろにある名前の出ない内部ラベル(`rp_ring`・`rp_x`)の時間が `hex_fast` に数えられていた。`.rst` から内部ラベルを拾い直して、`rp_x` だと分かった。

### 案 1: リングの読み直しのときに判定する(成り立たなかった)

**考え:** `rp_ring` はリングの中心と縮尺 q を表から読み、同じリングが続く間はそれを使い回す。その読み直しのときに 1 回だけ向きを判定して、結果を覚えておく。点ごとの処理は以前と同じ足し算 1 回に戻す。

**だめだった理由:** 縮尺の掛け算 `PSCALE` は q を符号なしとして扱う(`MULUW_HL_BC`)。q に符号を含めて覚えておくことができない。リングごとに覚えている中心 `rp_cx` のほうをいじっても、「cx から引く」形は点ごとの計算で作るしかない。結局、点ごとの分岐か符号反転が残る。説明の段階では、ここまで確かめずにこの案を勧めていた。

### 案 2: フレームごとに処理そのものを切り替える(途中で止めた・未実装)

**考え:**
- `rpt_a` / `rquad_a` を、u を足す版と引く版の 2 通り用意する。
- RAM に 3 バイトの `jp` を置き、env.c の呼び出しはそこを経由させる。
- `envm_draw` の始めに、`g_u_neg` に合わせて `jp` の飛び先を書き換える。
- 点ごとの判定は無くなり、1 回の呼び出しに `jp` が 1 つ増えるだけになる。

**気になる点:**
- 常駐部の空きが 495 B しかない。`PSCALE` を展開した部分を 2 通り持つと、およそ 200 B 増える見込み。
- RAM の `jp` は、最初の `envm_draw` より前に呼ばれると壊れる。今は env.c の飾りの描画からしか呼ばれないので問題ないが、注意が要る。

raster.s を書き換える前に止めた。そのあと案 4 を採用した。

### 案 3: `rp_x` を呼ばずにその場に展開する(未実施)

呼び出しと戻りの分だけ減る。分岐は残るので、0.23 ms のおよそ半分が減る見込み。案 2 よりも常駐部の増加が小さい。

### 案 4: 自己書き換えで `add` と `sbc` を差し替える(採用)

常駐部は、ローダー(src/boot/boot.s)が RAM のページ 1 へ写してから動かしている。そのため命令を書き換えられる(案 2・案 3 の検討では、常駐部が ROM 上で動くと思い込んでいた)。

- x を出す 3 か所(`rp_xop1`〜`3`)を `or a, a` + 2 バイトの命令にした。前向きは `add hl, de` / `nop`、後ろ向きは `sbc hl, de`。
- `rp_setdir`(raster.s)が、`envm_draw` の頭で 1 フレームに 1 回、この 2 バイトを書き換える。
- 常駐部の増加は 14 B(15889 → 15903 / 16384)。

結果:

| 測ったこと | 結果 |
|---|---|
| 前向き 30 秒 | 24.56 fps(40.7 ms)。v0.1.1 は 24.42 fps(40.9 ms)、`rp_x` 版は 24.23 fps(41.3 ms) |
| PC の記録 | `rpt_a` + `rquad_a` + `rp_xop1〜3` の合計は 2.186 ms。v0.1.1 の 2.168 ms との差は記録のぶれの範囲 |
| `make test` | PASS |
| 6 面の自動プレイ | PASS、ボス 8 体。平均 23.7 / 24.9 / 22.7 / 21.2 / 23.2 / 20.3 fps |
| 地形の絵 | 全 6 面、4 方向(0・67・112・180 度)の 708 枚を `rp_x` 版と比べた。アニメーションの時刻を止めると、違いは 6 面の風車の羽根 1 枚だけ。割り込みが時刻を進める位置がずれたためで、形の違いではない |

## 4. 真横の面(ボスを倒した後の見せ場)

地形の飾りは、レールを横切るリングの面に描いた平らな絵である。振り向きの途中で真横を向くと、この絵を端から見ることになり、何も見えなかった(1 面のお城は、真横を向くと消えていた)。

ボスを倒した後は敵が出ず、フレームが軽い。そこで、見せ場の大きな飾りだけ、レールに平行な面にも描くことにした。

| 面 | 飾り | 真横で描く面 |
|---|---|---|
| 1 | お城(右) | レール側の面(右 7.4m) |
| 3 | 祠(左)、鳥居の柱(左右) | 祠の手前の面、柱 |
| 4 | 灯台(左 22m) | 3D の点として投影する(どの向きでも同じ所に見える)。水平線のもやと向こう岸も描く |
| 6 | 農家(左右) | 道側の面(壁・角の柱・屋根の斜面)。最後の周回区間を抜けた後だけ |

### 描き方(env.c の `sp_begin` / `sp_col` / `sp_quad`)

- 面の上の縦の線は、カメラから同じ奥行きにある(見せ場は平らで、カメラが傾かない)。
- そこで縦の線ごとに足元を 1 回だけ投影し、それをリングの中心と q の代わりに置く。高さはリング面と同じ `rpt_a` で求める。
- 最初は点ごとに 3D の座標を作って `poly3` で塗った。真横の向きで地形の描画が 25 ms 増えたので、この形に変えた。
- 旗と花火は、真横からは画面の上の端より上に来るので描かない。花火は 8 個の四角を投影するだけで重く、描かないだけで 5 ms ほど減った。

### 重さ(地形の描画、FS-A1ST)

| 面 | 真横の向きの増加 | 区間の最大(変更前 → 変更後) |
|---|---|---|
| 1 | +6〜12 ms | 37.0 → 38.0 ms |
| 3 | +1〜8 ms | 36.8 → 36.9 ms |
| 4 | +2〜3 ms | 35.1 → 35.4 ms |
| 6 | +2〜12 ms | 41.5 → 45.7 ms |

- 前と後ろの向きは、4 面のボス後の区間(灯台の投影で +0.3〜1.1 ms)を除いて変わらない。
- ボスの前の区間(1 面の 34 の位置と向き)の地形の描画時間は、平均 +0.002 ms で変わらない。
- 6 面の自動プレイは PASS(ボス 8 体)。平均 fps は前の版と ±0.2 の差だった。2 面と 5 面はモジュールが同じでも ±0.2 動いたので、これはぶれの範囲とみる。

### 描いていないもの

- 3 面の森の木、4 面の鉄橋のトラス、5 面の家並みなど、面の全体にある飾りは真横で欠けたまま(ボスの前の重さに響くため)。
- 5 面の町の門と 2 面の岩の門は、中がトンネルなので、真横は壁が見えている。
