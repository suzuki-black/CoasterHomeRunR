# 詰めたバッファ + Z80 転送の計測 — 「詰めたバッファと Z80 転送の再検討」への回答

提案の 4 章（作り直す前に塗りだけを測る）を、仮定ではなく実際のゲームの塗りで行った。
あわせて、前回測っていなかった「Z80 で速く書いて VDP が取りこぼさないか」と「CPU の切り替えと割り込み」も確かめた。

結論:

- **詰めたバッファへの塗りは、いまより 9〜13% 遅い**（+0.3〜0.65ms/フレーム）。提案の判定基準（「超えるなら取り下げ」）では不合格。
- **それでも全体では得になる見込み**。Z80 転送で転送が 4ms 縮み、塗りの悪化を大きく上回る。
- 前回の私の判断（「描画全体を作り直す価値は無い」）は、詰め替えが消える効果を軽く見ていた。訂正する。

## 1. 実際の塗りの中身（記録）

ゲーム（ステージ 1、開始から 45 秒と 75 秒、各 12 フレーム）の塗り（raster.s の `fill`）の呼び出しを、openMSX のブレークポイントですべて記録した。

- 記録: tools/fillbench_log.tcl
- 集計: tools/fillbench_stats.py

| 1 フレームあたり | 45 秒 | 75 秒 |
|---|---|---|
| 呼び出し（面の数） | 29 | 30 |
| 塗る行（空でない行の数 = スパンの数） | 150 | 209 |
| 塗るブロック | 1,760 | 2,202 |
| 奇数の端（詰めた形では半バイトの読み書きになる） | 142 | 184 |
| 幅 2 ブロック以下のスパン | 40% | 39% |

1 回の呼び出しの時間を最小二乗で分解した（当てはまり R² = 0.993）。

| 部分 | 時間 | R800 のサイクル |
|---|---|---|
| ブロック 1 つ（`LD (HL),A` + `INC L`） | 0.80µs | 約 5.7 |
| 行 1 つ（左右の端を決め、展開した書き込みへ飛ぶ準備） | 約 11µs | 約 80 |
| 呼び出し 1 回 | 7.6µs | 約 55 |

- 塗りの時間のうち、ブロックを書く部分は約 4 割にとどまる。残りは行ごとの準備と呼び出しで、これは詰めた形にしても減らない。
- そのため、書き込みの数が半分になっても、塗りの時間は最大で 2 割ほどしか縮まない（提案の「書き込み半減で約 3.3ms」は成り立たない）。
- 一方、奇数の端は 1 フレーム 140〜180 か所あり、提案の仮定（500 スパンで約 2ms）より少ない。

raster.s の `fill` には以前から「push で 2 バイトずつ書く版も試したが、塗りの時間は 1 行ごとの準備で決まっていて速くならなかった」という記録があり、今回の分解と合っている。

## 2. 詰めたバッファへの塗りを書いて比べた（make fillbench）

詰めたバッファ（VRAM と同じ並び。Z80 が `OUTI` で頭から送れる形）へ塗る `pfill` を書いた（src/engine/fillbench.c）。

- 組み立ては `fill` と同じ（1 行ごとに左右を決め、展開した書き込みの途中へ飛ぶ）。
- 違いは「奇数の端の半バイトの読み書き」と「1 バイトごとに番地を +8」だけ。

記録した呼び出しをそのまま両方で再生して比べた（tools/fillbench_replay.tcl）。

| 場面 | いまの `fill` | `pfill`（詰めた形） | 差 | 絵の食い違い |
|---|---|---|---|---|
| 45 秒 | 3.96ms/フレーム | 4.30ms | **+0.34ms（+9%）** | 0 バイト |
| 75 秒 | 4.97ms/フレーム | 5.62ms | **+0.65ms（+13%）** | 0 バイト |

- 「絵の食い違い 0」は、両方で塗り終えたバッファを比べて確かめた（詰めた形を正しく塗れている）。
- 増えた分は、行ごとの番地の計算（列ペア × 8 + 行の下位 3 ビット）と、奇数の端の読み書き。書き込みが半分になって減った分（約 0.7〜0.9ms）を上回った。
- `pfill` は 1 回目の実装で、行ごとの番地を表引きにすれば多少は縮む余地がある。ただし、いまより速くなるところまでは見込めない。

## 3. それでも全体では得になる

塗りは悪化するが、転送で詰め替えが消え、Z80 で送れることの効果のほうが大きい。

| 方式 | 転送 | 塗りの悪化 | 合計の差 |
|---|---|---|---|
| いま（R800 が詰めながら送る） | 13.3ms | — | — |
| 詰めたバッファ + Z80 で送る | 0.9 + 8.4 = 9.3ms | +0.3〜0.65ms | **約 −3.4〜−3.7ms** |
| HUD 13 行を除外（R800） | 9.7ms | — | −3.6ms |
| HUD 除外 + 詰めたバッファ + Z80 | 0.9 + 6.1 = 7.0ms | +0.3〜0.65ms | **約 −5.7〜−6.0ms**（HUD 除外だけより −2.1〜−2.4ms） |

まだ測っていないもの（どれも小さいと見込むが、作り直しのときに測る）:

| 項目 | 向き | 見込み |
|---|---|---|
| 敵の矩形・縁取り（geom.s の `draw_model`）、文字、ポップアップ、コインの点 | 悪化（端の半バイトの読み書き） | 敵は面の数が少ないので 0.1〜0.3ms 程度 |
| 空と遠い地面の 2 色の行塗り（`buf_fill_rows`） | 改善（書くバイトが半分） | 0.1〜0.2ms 程度 |
| 割り込み処理（音）を Z80 で実行する時間 | 悪化 | 転送中に入ったときだけ。小さい |

## 4. 新たにわかった条件

### 4.1 Z80 で速く書いても VDP は取りこぼさない（openMSX）

VDP は速すぎる書き込みで CPU を待たせず、黙って取りこぼす。前回は時間だけを測っていたので、今回は確かめた。

- Z80 の `OUTI` の展開（5.45µs 間隔）で、表示中に 256 バイト書いた。
- それを R800 で読み戻したところ、食い違いは **0 バイト**だった。
- openMSX の `too_fast_vram_access` が `real`（取りこぼしを実機どおりに再現する設定）の状態で確かめた。

実機でも同じかは、`make vdpbench` の ROM の `ZERR` の行で確かめる（0 であること）。

### 4.2 BIOS の CHGCPU は、戻るときに割り込みを許可する

計測の結果、CHGCPU から戻った時点で割り込みが許可されていた。

- CHGCPU を呼ぶ間はページ0を BIOS に戻している。この間に VDP の割り込みが来ると、BIOS の割り込み処理がそれを受け、ゲーム側の割り込み処理（画面の切り替え・音）がそのフレームを取りこぼす。
- **対策: 切り替えの間だけ VDP の割り込み（R#1 の IE0）を止める。** 止めている間に帰線が始まっても S#0 の F フラグは立つので、IE0 を戻した直後に割り込みが入る。取りこぼさず、遅れるだけで済む。

### 4.3 割り込み処理は Z80 で動いてよい

- 割り込み処理と音の処理（sound.c）には、R800 専用の命令（MULUW など）が無い。
- 割り込み処理は画面の切り替えのときに VRAM の書き込み先を変える（スプライトの属性を書く）。ただし切り替えの要求は転送が終わってから出すので、転送の途中には入らない。いまの R800 の転送と同じ条件で済む。

## 5. 作り直しの範囲

描画バッファへ書く処理はすべて、詰めた形に合わせる必要がある。

| 処理 | 場所 | 内容 |
|---|---|---|
| 多角形の塗り | raster.s `fill` | `pfill` の形にする（今回のベンチの実装が土台になる） |
| 矩形・全体・行の塗り | gfx.s `rect_fill` / `buf_fill` / `buf_fill_rows` | 端の半バイト |
| 透過の絵・ランレングスの絵 | gfx.s `blit_trans` / `runs_draw`（乗り物） | ブロックごとの読み書き |
| 文字 | gfx.s `glyph1`、hud.c | 同上 |
| 敵と縁取り | geom.s `draw_model` | 矩形の端の半バイト |
| 点 | fx.c（コイン）、hud.c | 半バイトの読み書き |
| 転送 | vdp.s `vdp_xfer` | CPU の切り替え + Z80 の `OUTI` |

タイトル・コンフィグ・エンディングは同じバッファと転送を使うので、同時に移る。

## 6. 優先順位（改めて）

HUD 13 行の除外と、詰めたバッファ + Z80 転送は、どちらも転送の作り直しなので一つにまとめる。

| 順位 | 打ち手 | 見込み |
|---|---|---|
| 0 | 実機（ROM カートリッジ）で `make vdpbench` の ZERR = 0 と、Z80 の値を確かめる | 判定 |
| 1 | 帯の管理の作り直しの続き | 7.1 → 4〜5ms |
| 2 | HUD 13 行の除外 + 詰めたバッファ + Z80 転送（一度に作り直す） | 転送 13.3 → 7.0ms、塗り +0.3〜0.65ms。差し引き 約 −5.7ms |
| 3 | 変換・投影の C の部分をアセンブラへ | 約 3ms |
| 4 | 飾りの描き分け、描画距離の調整 | 面数枚分 |
| 後 | 行単位の差分転送（2 の「行ごとに送る・送らない」に乗せる） | 屋外で 1ms 前後 |

2 の見込みは 1 より大きい。ただし作り直しの範囲が広く、実機での確認（0）が前提になるので、0 の結果を見てから 1 と 2 の順番を決める。

